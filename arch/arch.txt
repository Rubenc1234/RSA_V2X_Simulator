===============================================================================
ARQUITETURA DE SIMULAÇÃO C-ITS 100% DESCENTRALIZADA (VERSÃO V2)
===============================================================================
Este documento define a especificação arquitetural do simulador V2X distribuído.
Ao contrário da abordagem monolítica anterior, esta arquitetura elimina qualquer
orquestrador centralizado de física (antigo simulator_core.py). Cada OBU corre 
isolada no seu próprio container Docker como um agente inteligente e autónomo, 
gerindo localmente a sua física, rede e tomada de decisões.

-------------------------------------------------------------------------------
1. DIAGRAMA DE COMPONENTES E FLUXO POR NÓ (CONTAINER OBU)
-------------------------------------------------------------------------------

+---------------------------------------------------------------------------+
|                           DOCKER CONTAINER (OBU NÓ)                       |
|                                                                           |
|   [obu_main_v2.py] <--- Ponto de entrada (Entrypoint / Thin Bootstrap)    |
|         │                                                                 |
|         ▼ Instancia e delega a execução para                              |
|   [car_agent_v2.py] <--- Controlador de Rede (DecentralizedCarAgent)      |
|         │                                                                 |
|         ├─── [Thread 1: MQTT Client] ◄═══► [Broker Local Vanetza-NAP]     |
|         │         (Escuta: vanetza/out/* | Publica: vanetza/in/*)         |
|         │                                                                 |
|         └─── [Thread 2: Loop Local] ◄─── Loop de Física Autónomo (5Hz)    |
|                   │                                                       |
|                   ▼ Encapsula, Atualiza Estado e Invoca Métodos           |
|             [Vehicle] <--- Entidade Pura de Domínio (domain/vehicle.py)   |
|                   │                                                       |
|                   ├─── [DENMRegistry] <--- Memória Privada de Perigos     |
|                   │                                                       |
|                   └─── [EventTriggerEngine] <-- Motor Local de Regras     |
|                             │                                             |
|                             └─► Analisa Mundo: [my_vehicle] + [Neighbors] |
+---------------------------------------------------------------------------+

-------------------------------------------------------------------------------
2. RESPONSABILIDADE DOS FICHEIROS E PADRÕES DE DESIGN
-------------------------------------------------------------------------------

A arquitetura segue os princípios de Separation of Concerns (SoC) e Domain-Driven 
Design (DDD), isolando a lógica de negócio (física e C-ITS) dos protocolos de rede.

📁 1. CAMADA DE INFRAESTRUTURA E CONFIGURAÇÃO ESTÁTICA
   ├── docker-compose.yml
   │   └── Propósito: Providencia o isolamento completo de hardware e rede (VLAN).
   │       Instancia os pares de containers por veículo (um Codec Vanetza para 
   │       UPER/ITS-G5 e um agente Python de controlo). Garante IPs estáticos
   │       e isolamento total de memória entre as OBUs.
   └── scenarios/registry.py
       └── Propósito: Fonte Única de Verdade (Single Source of Truth) estática.
           Contém as coordenadas geográficas de rotas (start/end), velocidades
           e constantes físicas (ex: proximidade de 45m). Cada OBU lê APENAS
           a secção que lhe diz respeito no bootstrap, ignorando os rivais.

📁 2. CAMADA DE REDE, ORQUESTRAÇÃO LOCAL E AGENTES
   ├── agents/obu_main_v2.py
   │   └── Propósito: Entrypoint leve do container Docker. A sua única função
   │       é ler as variáveis de ambiente (VEHICLE_NAME, SIM_SCENARIO), ir ao
   │       registry.py extrair o perfil local e arrancar o Agente de Rede.
   ├── agents/car_agent_v2.py
   │   └── Propósito: O "Middleware" ou Maestro do nó. É focado puramente em I/O.
   │       - Mantém uma thread com o loop de física (`physics_loop`) a 5Hz.
   │       - Transforma pacotes de rede (JSON das filas MQTT do Vanetza) em 
   │         comandos de alteração de estado para a classe Vehicle.
   │       - Mantém um dicionário na memória local chamado `neighbor_vehicles`,
   │         onde guarda "Veículos Fantasmas" criados a partir dos CAMs recebidos.

📁 3. CAMADA DE DOMÍNIO (DOMAIN ENTITIES)
   ├── domain/vehicle.py
   │   └── Propósito: Entidade Pura de Domínio. Não possui importações de MQTT,
   │       sockets ou frameworks de rede.
   │       - Controla a cinemática própria (latitude, longitude, heading, velocidade).
   │       - Consome waypoints geográficos (OSRM) para navegar de forma autónoma.
   │       - Gere o estado de Burst (rajada de DENM) validado por tempo lógico 
   │         através de `should_publish_collision_denm(sim_time)`.
   ├── domain/denm_registry.py
   │   └── Propósito: A memória RAM de ameaças do veículo. Cada OBU tem o seu.
   │       - Analisa os JSONs de alertas DENM recebidos pelo ar.
   │       - Regista as ameaças ativas usando o tempo lógico da simulação.
   │       - Executa `clean_expired_events()` com base no `latest_sim_time`.

📁 4. CAMADA DE SENSÓRICA VIRTUAL (MOTOR DE EVENTOS)
   └── domain/eventTrigger.py
       └── Propósito: Motor Local de Regras Baseado em Condições.
           - Corre localmente no cérebro de cada OBU.
           - Recebe o ecossistema local unificado (`all_visible_world`) e avalia,
             se o contexto gera um perigo iminente.

🛑 O ESTADO DO FICHEIRO `simulator_core.py`:
   - Este componente monolítico/centralizado foi COMPLETAMENTE REMOVIDO da lógica 
     de execução ativa das OBUs. Nenhum container de agente depende dele para se mover.
   - O seu propósito atual é estritamente passivo (Observador/Dashboard externo) 
     para subscrever a rede e visualizar/logar o mapa de forma global.

-------------------------------------------------------------------------------
3. MECANISMO DE SINCRONIZAÇÃO E PERCEPÇÃO (COMO A DESCENTRALIZAÇÃO FUNCIONA)
-------------------------------------------------------------------------------

Sem um servidor centralizado que saiba onde estão todos os carros, as OBUs aplicam
o conceito de "Percepção Cooperativa Espelhada":

1. O CICLO DE CONSCIÊNCIA PRÓPRIA (SAÍDA / OUTBOUND):
   A cada 200ms, o `physics_loop` instrui o `my_vehicle` a avançar na rota. O agente 
   extrai as novas coordenadas e publica no tópico `vanetza/in/cam`. O Vanetza 
   codifica em UPER binário e injeta na antena ITS-G5 simulada.

2. O CONCEITO DE "VEÍCULOS FANTASMAS" (ENTRADA / INBOUND):
   Quando uma OBU vizinha emite um CAM, o `car_agent_v2.py` interceta o JSON vindo 
   de `vanetza/out/cam`, extrai o `stationId` e:
   - Se o ID for novo: Instancia um novo objeto `Vehicle` na sua cache local 
     `neighbor_vehicles` (um clone/fantasma do rival).
   - Se o ID já existir: Atualiza as variáveis cinemáticas desse fantasma.

3. DETECÇÃO DE RISCO E INFRAESTRUTURA C-ITS AUTÓNOMA:
   No fim do tick, o agente monta um mapa local (`all_visible_world`) contendo o seu 
   `my_vehicle` e os `neighbor_vehicles`. O `EventTriggerEngine` calcula as distâncias.
   Se o risco for detetado (Ex: <45m), o veículo real ativa o seu estado de emergência
   (`start_collision_burst()`) e passa a ditar a publicação autónoma de DENMs.

4. REACÇÃO COMPORTAMENTAL A ALERTAS:
   Se uma OBU capta uma DENM, regista-a no seu `DENMRegistry` privado. A entidade 
   `Vehicle` própria lê este registo em cada ciclo e altera autonomamente a sua 
   cinemática (aplica travagem de override ou recalcula comportamento).
